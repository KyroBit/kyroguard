# Typing policies with rbac.d.ts

In this guide you generate a declaration file from your policy definitions so policy names are checked at compile time — a typo in `requirePolicy` becomes a build error instead of a mystery 403 in production.

::: tip Prerequisites
You have policy files and an `rbac.config.ts` ([Syncing policies](/guide/syncing-policies)), and at least one portal with guards ([Protecting routes](/guide/protecting-routes)).
:::

## Generating the file

1. Point `rbac.config.ts` at your policy files and choose an output path:

```ts
// rbac.config.ts
import { defineConfig } from '@kyrobit/rbac'

export default defineConfig({
  adapter: async () => {
    const { drizzleAdapter } = await import('@kyrobit/rbac/drizzle')
    const schema = await import('./src/db/rbac-schema.js')
    const { db } = await import('./src/db/index.js')
    return drizzleAdapter(db, { schema })
  },
  portals: [
    { name: 'admin', policies: './src/rbac/admin/policies.ts', groups: './src/rbac/admin/groups.ts' },
    { name: 'branch', policies: './src/rbac/branch/policies.ts' },
  ],
  typegen: { output: './rbac.d.ts' }, // the default; resolved relative to the config file
})
```

2. Run either command:

```sh
npx rbac generate   # typegen only — reads your policy files, never opens a database
npx rbac sync       # pushes policies + groups to storage, THEN writes the same file
```

Both write `rbac.d.ts`. Use `generate` in fast local loops and CI type checks; `sync` regenerates as a side effect of every deploy-time sync, so types can never lag behind what storage enforces.

3. For an `admin` portal defining `posts.read`, `posts.create`, `posts.update` and a `branch` portal defining only `posts.read`, the generated file is:

```ts
// Generated by `rbac sync` / `rbac generate` — do not edit.

export {}

declare module '@kyrobit/rbac' {
  interface RbacTypes {
    Portal: "admin" | "branch"
    PolicyName: "posts.create" | "posts.read" | "posts.update"
    PortalPolicies: {
      "admin": "posts.create" | "posts.read" | "posts.update"
      "branch": "posts.read"
    }
  }
}
```

Names stay unqualified — the portal prefix is added at runtime by the engine. Every literal (union members and property keys alike) is emitted through `JSON.stringify`, so a policy name containing quotes or unusual characters cannot break, or inject code into, the declaration.

4. Include the file in `tsconfig.json`. If your `include` lists specific directories, TypeScript never loads the augmentation unless the file is listed too:

```json
{
  "include": ["src", "rbac.d.ts"]
}
```

## What the augmentation gives you

With the file in place, guard and assignment sugar on each portal accepts only that portal's policy union:

```ts
const portal = app.rbac.portal('admin', { getSubject })

portal.requirePolicy('posts.update') // OK — member of PortalPolicies['admin']

portal.requirePolicy('posts.raed')
// error TS2345: Argument of type '"posts.raed"' is not assignable to parameter
// of type '"posts.create" | "posts.read" | "posts.update"'.

await portal.assignPolicy('user_42', 'posts.update', { scope: 'owned' }) // name checked here too
```

A `branch` portal rejects `posts.update` outright, because it is not in `PortalPolicies['branch']` — cross-portal copy-paste mistakes fail at compile time.

For your own signatures, the resolved unions are exported as type aliases: `PortalName` (the `Portal` union), `AnyPolicyName` (all policies across portals) and `PortalPolicyName<P>` (one portal's union):

```ts
import type { PortalName, PortalPolicyName } from '@kyrobit/rbac'

function auditGrant(portal: PortalName, policy: PortalPolicyName<'admin'>): void { /* ... */ }
```

The low-level `rbac.admin.assignPolicy` is intentionally untyped beyond `string` — it takes fully qualified names (`admin.posts.update`) and exists for generic tooling; prefer the portal sugar in app code.

## How the empty-interface resolution works

The library ships `RbacTypes` as an **empty** interface, and every consumer type is conditional on it:

```ts
// inside @kyrobit/rbac
export interface RbacTypes {}

export type PortalPolicyName<P extends string> = RbacTypes extends { PortalPolicies: infer M }
  ? P extends keyof M
    ? M[P] & string
    : string
  : string
```

Two mechanics matter:

- **Augmentation ADDS members.** TypeScript merges interface declarations, but rejects re-declaring an existing property with a narrower type. If the library shipped `Portal: string`, your `Portal: 'admin' | 'branch'` would be an illegal re-declaration — shipping the interface empty is what makes the augmentation possible at all.
- **`export {}` makes the generated file a module.** That turns the `declare module '@kyrobit/rbac'` block into an augmentation of the real package instead of an ambient module declaration that would replace its types.

Guards pick this up automatically: `requirePolicy` is declared as `requirePolicy(policy: PortalPolicyName<P>, ...)`, and `P` is inferred from the string literal you pass to `portal('admin', ...)`.

::: warning Degradation is silent
Before augmentation, every conditional falls back to `string` — the library works with zero codegen, which is why nothing errors when the setup is incomplete. The consequence: if `rbac.d.ts` is missing from `include`, or you create a portal whose name is not a key of `PortalPolicies` (`app.rbac.portal('amin', ...)`), guards quietly accept any string again. After setup, verify the types are live by hovering `requirePolicy` or deliberately misspelling a policy name and confirming the compile error appears.
:::

## Regenerating on policy changes

The file mirrors your policy definitions at the moment it was generated. Whenever you add, rename or remove a policy or portal:

```sh
npx rbac generate
```

Practical setup:

```json
{
  "scripts": {
    "rbac:types": "rbac generate",
    "typecheck": "rbac generate && tsc --noEmit"
  }
}
```

Running `generate` before `tsc` in CI means a stale committed `rbac.d.ts` is rewritten before checking, and any code still referencing a removed policy fails the build. A stale file fails in the safe direction — new policy names are rejected at compile time until you regenerate, rather than unknown names being accepted.
