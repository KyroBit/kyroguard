# Syncing policies

`rbac sync` pushes your policy and group files into storage and regenerates the typed policy names. On this page you run a sync, read what each step does to your data, wire the command into CI and deploys, and call the same pipeline programmatically.

::: tip Prerequisites
You need a `policies.ts` and (optionally) a `groups.ts` registered in `rbac.config.ts` — see [Defining policies](/guide/defining-policies) and [Organizing groups](/guide/organizing-groups).
:::

## Running a sync

### 1. Run your migrations first

Sync writes rows, not tables. With Drizzle, the rbac schema file is part of your migration set:

```sh
npx drizzle-kit migrate
```

If the tables are missing, sync fails with exit code 1 and tells you why:

```
[rbac] sync failed: relation "rbac_policies" does not exist
[rbac] The rbac tables do not exist yet — run your migrations first (drizzle-kit push / migrate).
```

### 2. Run the sync

```sh
npx rbac sync
```

The command finds `rbac.config.{ts,mts,mjs,js}` in the current directory (or takes `--config <path>`), loads `.env`, and runs TypeScript config files directly — natively under Bun, via jiti under Node, no build step. A run against the blog example prints:

```
[rbac] Synced 7 policies.
[rbac] Seeded 3 groups for portal "admin".
[rbac] Wrote /app/rbac.d.ts
```

### 3. Commit the generated types

`rbac.d.ts` augments the `RbacTypes` interface so portal and policy names are string-literal unions:

```ts
// Generated by `rbac sync` / `rbac generate` — do not edit.

export {}

declare module '@kyrobit/rbac' {
  interface RbacTypes {
    Portal: "admin"
    PolicyName: "comments.moderate" | "comments.view" | "posts.create" | "posts.delete" | "posts.publish" | "posts.update" | "posts.view"
    PortalPolicies: {
      "admin": "comments.moderate" | "comments.view" | "posts.create" | "posts.delete" | "posts.publish" | "posts.update" | "posts.view"
    }
  }
}
```

Commit it so `requirePolicy` autocompletes for everyone. To regenerate it without a database (in a typecheck-only CI job, for example), run `npx rbac generate` — it reads only your policy files.

## What a sync run does

One run works through this pipeline, in order:

1. **`ensureSchema`** — the adapter's optional DDL hook runs once, before anything is written. It is idempotent, so calling it on every run is safe. Drizzle and Prisma have none (migrations own DDL); Mongoose syncs indexes.
2. Then, **per portal** in config order:
   1. **Load and validate** — the portal's `resources` module is loaded and every `dependsOn` entry is checked against the portal's policy list. An unknown dependency aborts the run before any write.
   2. **Upsert** — every policy is written with its qualified name and the portal recorded in a stored column. Existing policies are updated in place: **label, `scopeOptions` and `dependsOn` all change on re-sync**, with stable row ids, so editing a label in code is enough to change it everywhere.
   3. **Orphan cleanup** — stored policies whose portal column matches this portal but whose name no longer appears in code are deleted. The filter is the stored portal column, never a guess from the name's shape, so syncing one portal cannot delete another portal's policies — that is what makes per-portal syncs safe to run independently.
   4. **Group seed** — if the portal has a `groups` file, each group in it is upserted and its entries are set to exactly the seed list ([replace-all per group](/guide/organizing-groups#what-re-seeding-does)).
   5. **Dependency back-fill** — every stored group is walked and missing transitive dependencies are added as unrestricted grants (existing entries keep their scopes). Granting `posts.create` to a group fills `posts.view` on this step, and because it runs after the seed, seed lists never need to repeat dependencies.
3. **Typegen** — `rbac.d.ts` is rewritten from the synced policy names.

Two built-in safety rails: a portal whose policy list is empty returns early instead of treating everything as orphaned — a broken import can never wipe a portal. And the whole pipeline is idempotent: running it twice in a row changes nothing the second time, so re-running on every deploy is the intended usage.

::: danger Removing a policy from code removes access on the next sync
Orphan cleanup **cascades**: deleting a policy also deletes every group entry and every direct assignment that references it, in the same cleanup (SQL adapters wrap it in a transaction). Renaming counts — `posts.write` renamed to `posts.update` is a delete plus a create, and no assignment carries over. After the sync, every request guarded by the removed name is denied with 403:

```json
{
  "message": "Forbidden",
  "code": "RBAC_POLICY_DENIED"
}
```

There is no undo: re-adding the policy restores the definition, not the assignments. Before deleting or renaming a policy in `policies.ts`, check what references it (`rbac status` shows stored counts; query `rbac_policy_group_policies` and `rbac_user_policies` for the specifics) and plan to re-grant.
:::

## Syncing in CI and deploys

Run migrations, then sync, then start the app — in that order, because sync needs the tables and the app needs the synced policies:

```json
// package.json
{
  "scripts": {
    "deploy": "drizzle-kit migrate && rbac sync && node dist/server.js"
  }
}
```

Or as pipeline steps:

```yaml
# .github/workflows/deploy.yml (excerpt)
- run: npx drizzle-kit migrate
- run: npx rbac sync
  env:
    DATABASE_URL: ${{ secrets.DATABASE_URL }}
```

`rbac sync` exits non-zero on failure, so a broken policy file (for example an unknown `dependsOn`) fails the deploy instead of the first request.

::: warning Running instances stay stale for one cache TTL
Sync runs in its own process and cannot invalidate the caches inside your running app instances. After a sync, an instance keeps serving its cached policy maps until they expire — 30 seconds with the default memory cache. If a revoked permission must die faster than your TTL, have the app call `rbac.cache.clear()` (for example from a deploy webhook), or shorten the TTL. See [Policy cache](/guide/caching).
:::

## Syncing programmatically

The same pipeline pieces are methods on the `rbac` instance, for setups that sync at boot or from a script instead of the CLI:

```ts
import { createRbac } from '@kyrobit/rbac'
import { drizzleAdapter } from '@kyrobit/rbac/drizzle'
import * as schema from './db/rbac-schema.js'
import { db } from './db/index.js'
import { resources } from './rbac/policies.js'
import { groups } from './rbac/groups.js'

const rbac = createRbac({ adapter: drizzleAdapter(db, { schema }), resources, db })

// ensureSchema → upsert → orphan cleanup → back-fill (no seeding, no typegen):
await rbac.sync(resources, 'admin')

// Group seeding is separate; pass the policy list so `policies: 'all'` resolves:
await rbac.seedGroups(groups, resources.flatMap(r => r.policies), 'admin')

// This process now has stale cached policy maps — drop them:
await rbac.cache.clear()
```

Differences from the CLI: `rbac.sync()` never seeds groups and never writes `rbac.d.ts` — call `rbac.seedGroups()` yourself and use `rbac generate` for types. Omit the portal argument for a portal-less setup; names then stay unqualified.
